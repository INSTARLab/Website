# Contributing to instarlab.org

This repo is the source for [instarlab.org](https://instarlab.org), the
website of INSTAR Lab Inc., a real 501(c)(3) nonprofit research
institute. It is a **hand-authored static HTML/CSS/JS site** — please
read this whole document before opening a PR, since several of its
conventions are easy to violate by accident.

## No build system

There is no `package.json`, no bundler, and no task runner. Pages are
raw `.html` files edited by hand, and there are no linters,
formatters, or automated tests. `scripts/build-css.sh` and
`scripts/build-js.sh` exist, but they are one-shot concatenation/
minification helpers (via `clean-css-cli` / `terser` through `npx`),
not a persistent build pipeline — source files (`css/*.css`,
`style.css`, and this site's own `js/*.js`) stay hand-editable, and
those scripts just re-flatten them into `master.css` / `*.min.js`
after you change a source file. Run them from the repo root if your
change touches those source files; don't hand-edit the generated
`master.css` or `*.min.js` outputs directly.

Because nothing is generated by a build step for HTML, "verifying"
a change means opening the affected page(s) in a browser and checking
them by eye.

## Nav and footer are duplicated inline in every page

There is no include/partial/template mechanism, and `main.js` does
not inject shared markup. The navigation bar and footer are copy-
pasted into every one of the ~63 `.html` files in this repo. If your
change touches nav or footer markup (a new link, a wording change, a
new menu item), it must be propagated **by hand** to every file that
contains it. If you're working with Claude Code, the `/propagate-nav`
skill in this repo automates that propagation — use it rather than
editing files one at a time.

## Images are AVIF-only

All page imagery follows the layout
`img/pages/<page>/{hero,inline-N,card-N,section-N}.avif`. Never add a
new `.jpg`, `.jpeg`, `.png`, or `.webp` image reference — several past
commits in this repo's history exist solely to fix pages that ended
up pointing at missing JPGs. If you're adding imagery for a new page
or section, convert it to AVIF and follow the existing naming
pattern.

## This is a real nonprofit — don't fabricate facts

INSTAR Lab Inc. is a verified 501(c)(3) public charity
(170(b)(1)(A)(vi)). Do not invent EINs, financial figures,
credentials, partner names, statistics, or other factual claims when
writing or editing copy. If a claim needs a fact you can't verify
from existing site content or a linked/cited source, leave it out or
flag it in the PR rather than guessing.

## CSS

`master.css` at the repo root is the single stylesheet entry point
that pages link to (`href="master.css"` at root depth,
`href="../../master.css"` two directories deep, etc.). It's generated
by `scripts/build-css.sh` from `css/bootstrap.min.css`,
`css/heading.css`, `css/animate.css`, `css/main.css`, `style.css`,
`css/interior-pages.css`, and `css/responsive.css`, in that order.

- Edit `style.css` (repo root) for site-specific overrides.
- Don't edit the vendored `css/` template files unless you're
  intentionally patching the vendored template itself.
- After editing `style.css` or any of the vendored `css/` sources,
  re-run `./scripts/build-css.sh` to regenerate `master.css`.

The `switcher/` theme switcher is **dormant** — its
`js/styleswitch.js` include is commented out on the homepage. Don't
wire it up unless a task explicitly asks for it.

## Structure

- Root pages: `index`, `about`, `mission`, `contact-us`, `privacy`,
  `terms`, `accessibility`, `404`.
- Sectioned content uses clean-URL directories (`<topic>/index.html`):
  `sciences/` (22 disciplines), `technology/` (7), `research/` (7),
  plus `community/`, `tech-transfer/`, `labs/`, `news/`, `fellowship/`.
- Shared assets live in `css/`, `js/`, `fonts/`, `switcher/`, `img/`.
- `nav-preview.html` and `issue-triage.html`, if present locally, are
  **gitignored local-only mockups** — never treat them as production
  pages or commit them.

If you add a new page, add it to `sitemap.xml` (hand-maintained) and
make sure it's reachable from the nav/footer if it should be.

## Forms and mail

Live, working forms on the site are plain JavaScript (for example the
site's own `contact-us.js`, `community/contact/intake.js`, and
`community/partner/partner-form.js`) — check the relevant page/form
directory for the current script before assuming a form's wiring.
`mail.php` is a legacy PHP contact mailer kept in the repo for
reference, but **PHP does not run on GitHub Pages**, so it is dead on
the live deployment; don't build new functionality on top of it.

## Deploy

This repo is **GitLab-first**, mirrored to GitHub Pages.
`.gitlab-ci.yml` includes the `DroidOpsInc/launch-sequence` pipeline
(`/pipelines/static-site.yml`, `SITE_DIR="."`,
`GITHUB_REPO="INSTARLab/Website"`), which publishes to GitHub. GitHub
Pages then serves the `gh-pages` branch at instarlab.org via `CNAME`.
`sitemap.xml` and `robots.txt` are hand-maintained, not generated.

## Opening an issue or PR

- Use the issue templates under `.github/ISSUE_TEMPLATE/` — they
  enforce a Problem / Evidence / Acceptance-criteria format so
  reviewers (human or agent) have a concrete checklist to close
  against.
- Use the PR template under `.github/PULL_REQUEST_TEMPLATE.md` and
  work through its checklist (AVIF-only imagery, hand-propagated
  nav/footer, no fabricated facts, `sitemap.xml` updates) before
  requesting review.
- Review is routed via `.github/CODEOWNERS`.

## Questions

If something in this document is unclear or seems out of date versus
what you find in the codebase, open an issue rather than guessing —
this file should track the site's actual conventions, not the other
way around.
